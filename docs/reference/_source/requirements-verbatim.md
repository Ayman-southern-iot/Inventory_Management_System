## 1. Overview

This document defines the functional requirements for an internal inventory management system
covering procurement requests, approvals, fund tracking, inventory logging, and reporting.

## 2. Roles

- **General** — submits procurement requests.
- **Approver** — approves or rejects requests; can toggle a delegate to approve on their behalf
  when away.
- **Inventory Manager** — generates the Bill of Materials, logs funds received, tracks purchased
  inventory, and logs returns.

## 3. Procurement Request Form

A single request can include one or more items. Each item line captures its own name and
quantity. Urgency, deadline for approval, reason, department, and linked project are set once per
request and apply to all items within it.

| Field | Scope | Notes |
|---|---|---|
| Item name | Per line | One or more items per request |
| Quantity | Per line | |
| Urgency | Per request | Applies to all items in the request |
| Deadline for approval | Per request | Triggers the notification flow (see Section 5) |
| Reason | Per request | |
| Department | Per request | |
| Project | Per request | Feeds into the Bill of Materials |

## 4. Approval Flow

- Expense threshold: 15,000 BDT, configurable by an admin for future changes.
- Requests above the threshold require exactly 2 approvers. No fixed sequence — either approver
  can act first.
- If either of the 2 approvers rejects the request, the whole request is rejected. It does not
  require both to reject.
- An approver can toggle on a delegate to approve on their behalf while they are away, instead
  of the request stalling or being auto-rejected.
- Approvers can see which assigned approver(s) have not yet responded.

## 5. Notifications

- If an approver has not approved or rejected a request by its approval deadline, they are
  pinged with a reminder.
- If a request is rejected, the original requester is notified.

## 6. Fund Logging

- The Inventory Manager logs funds received against the specific procurement request (requested
  amount vs. approved amount vs. funded amount).
- Funding can be partial — e.g. 50,000 BDT approved, 30,000 BDT released now, remainder released
  later.
- There is no automatic notification when remaining funds arrive; the Inventory Manager checks
  back on the request manually.

## 7. Inventory Tracking

- Each item is assigned a Storage ID and a manually entered location.
- Only laptops and R&D hardware are logged in the system at this stage — furniture is not
  tracked for now.
- These tracked categories are movable, and the system keeps a history of location changes.

## 8. Returns

- Returned items are logged back into storage.
- Once returned, an item becomes available for internal reissue to another requester.

## 9. Bill of Materials (BOM)

Generated and printed by the Inventory Manager, auto-filled from the originating request form
submission(s).

| Field | Source |
|---|---|
| Item | Auto-filled from request |
| Quantity | Auto-filled from request |
| Unit cost | Entered by Inventory Manager |
| Total cost | Calculated |
| Vendor | Free text, entered by Inventory Manager |
| Purpose | Auto-filled from request (reason) |
| Linked project | Auto-filled from request |

## 10. Export & Reporting

- Bill of Materials and inventory records can be exported as PDF for the Inventory Manager to
  submit physical copies to the accounts department.
- No low-stock alerting is required at this stage.

## 11. Open Items / Future Configuration

- Expense threshold (currently 15,000 BDT) should be adjustable by an admin without a code
  change.
- Movable/trackable item categories are currently limited to laptops and R&D hardware; this list
  should be extendable later (e.g. furniture).

## Reader's notes — what this document does *not* say

Kept here deliberately, because the gaps are what cause misclassification. None of the following
appears anywhere above:

- **No Admin role.** §2 defines three roles. "Admin" appears only obliquely, in §11
  ("adjustable by an admin"). The fourth role is derived.
- **No Inventory Manager approval stage.** §4 describes a 2-approver flow. The IM-confirms-first
  stage is derived, from the user story rather than this document.
- **Nothing about how many approvers below the threshold.** §4 specifies *above* only.
  Filled by `OQ-01` (answered by the operator 2026-07-29): 1 below, 2 at-or-above.
- **Nothing about a request exactly equal to the threshold** in this document. §4 says "above the
  threshold require exactly 2". `OQ-01`'s answer says "at or above the threshold it stays 2",
  which resolves it; the code matches (`requisitions.service.ts:216`).
- **No borrow loop.** §8 is two sentences about returns. Reservations, borrow requests, issue,
  partial returns, condition recording, and **quarantine** are all derived.
- **No self-approval rule.** Nothing prohibits an approver approving their own request. The
  entire substitution mechanism is derived.
- **No over-budget rule**, no BOM bounce-back, no send-back-for-revision.
- **No transportation cost**, no supporting document, no funding snapshots, no unverify-purchase.
- **Only two notifications** (§5): the deadline reminder and the rejection notice. The other
  eight rows of the notification matrix are derived.
- **No "Remaining" column on the BOM** (§9 lists seven columns) and no approver footprints block.
- **Location is "manually entered"** (§7), and each item has a "Storage ID". The structured
  zone → compartment → placement model is a deliberate replacement, not an implementation of it.

Derived is not wrong. But it is classified `DERIVED` or `NO-BASIS`, never `REQUIRED`.
