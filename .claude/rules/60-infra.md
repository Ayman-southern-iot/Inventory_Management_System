# Infrastructure

## The rule that matters

**A deploy must never be able to lose data.** Everything else here is in service of that.

- Postgres data lives in the named volume `ims_pgdata`. Never bind-mount it, never anonymise it.
- The Postgres image is pinned to a major version. Bumping the major is a planned dump-and-restore,
  never a tag change.
- `docker compose down -v` and `docker system prune --volumes` are forbidden. `deploy.sh` never
  calls `down` at all.
- Migrations run as a one-shot `migrate` service that must exit 0 before `api` starts. A failed
  migration means a stopped deploy, not a half-migrated live system.
- `deploy.sh` takes a backup before doing anything else.

## Images

- Multi-stage builds, non-root user, no build toolchain in the runtime layer.
- Pin base images by major+minor. Never `:latest`.
- No secrets in images or build args. Secrets arrive via `env_file` at runtime.
- Healthchecks on `api` and `db`; compose ordering depends on them, not on `sleep`.

## What lives where

`infra/` holds compose, Caddyfile, `.env.example`, and the deploy/backup/restore scripts.
`.env` itself is never committed and never generated by a script that writes real secrets to disk
outside the VM.
